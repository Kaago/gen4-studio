# Release 1.0.1: Auto-Update und Nacharbeiten — Implementierungsplan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Gen4 Studio 1.0.1 holt neue Versionen selbst aus GitHub Releases (signiert, mit Zustimmung) und schließt die für 1.0.1 gesammelten Nacharbeiten aus 1.0.0.

**Architecture:** Teil A baut den Updater: eigene Rust-Befehle um `tauri-plugin-updater` (kein npm-Paket), ein Hook mit Einstellungen in `localStorage` und Toasts in der Oberfläche, Update-Pakete und `latest.json` in beiden Release-Pfaden. Teil B räumt Sprachwechsel, Textvergleiche, Rest-Englisch und Kleinkram auf. Teil C prüft den Updater mit zwei rc-Releases echt und veröffentlicht 1.0.1. Gearbeitet wird auf dem Branch `r101` (Worktree), Tasks in eigenen Worktrees davon; `r101` geht nach dem Gate nach `main`.

**Tech Stack:** Rust 2024, Tauri 2.12 (`tauri-plugin-updater` 2), rust-i18n 4.2.4, React 19, TypeScript, i18next 27, vitest, bash 3.2, `gh`, GitHub Actions.

**Spec:** [docs/superpowers/specs/2026-11-11-release-1-0-1-design.md](../specs/2026-11-11-release-1-0-1-design.md)

## Global Constraints

- Codes bleiben: `CmdError.code`-Werte, Prüfcodes, MCP-Werkzeugnamen und ihre Argumente ändern sich nicht. Neu sind nur der Code `"reopen"` (Task 10) und die Befehle `update_check` und `update_install` (`APP_ONLY`, Task 2).
- Englisch ist Standard und Fallback, Deutsch vollständig. Jede neue Zeichenkette steht in beiden Katalogen: Frontend `apps/studio/src/i18n/locales/{en,de}/*.json` (Schlüssel `camelCase`, Platzhalter `{{name}}`), Rust `locales/{en,de}.yml` (Schlüssel `module.snake_case`, Platzhalter `%{name}`). Kein `t()` auf Modulebene.
- Frontend-Tests laufen mit `lng: "de"` und sichern deutsche Texte zu; Rust-Tests sichern Englisch zu. Amerikanische Schreibweise. Die deutsche Oberfläche spricht niemanden direkt an (kein „du“, kein „Sie“).
- Bindendes Vokabular wie in 1.0.0 (`docs/glossary.md`, `docs/en/glossary.md`).
- Der Updater ist nur in der gepackten App aktiv: `inTauri() && !import.meta.env.DEV`. Außer der Update-Prüfung gibt es keinen neuen Netzzugriff; kein neues npm-Paket.
- Privater Schlüssel und Passwort stehen nie im Repository, in Logs, in Ausgaben oder im Klartext in einer Befehlszeile. Skripte geben sie nie aus.
- `deny.toml` wird nicht still geändert: Verlangt `cargo deny` eine neue Lizenz, hält der Controller an und fragt den Maintainer.
- Shell-Skripte laufen auf bash 3.2 und Git Bash; Tests als `scripts/tests/*.test.sh` mit `scripts/tests/lib.sh`. Meldungen der Release-Skripte sind Deutsch (in `release.yml` ohne Umlaute, wie bisher).
- Keine neuen GitHub Actions; jede `uses:`-Zeile bleibt auf einen SHA festgelegt (`scripts/check-actions.sh`).
- Fassung nur über `scripts/version.sh`. Vor jedem `release.yml` läuft `gh workflow run ci.yml -f windows=true` auf demselben Commit grün.
- Keine ROM-Daten (`scripts/check-no-rom-data.sh` bleibt grün); DSPRE nie „based on“ oder „fork of“.
- CSS nur mit Tokens (`scripts/check-styles.sh`); neue Spalten der Einstellungen nehmen die Klassen aus `SettingsArea.module.css`.
- Subagenten: Sonnet; Task 9 und die abschließende Review auf Opus.

## Review Focus

1. Offline oder GitHub nicht erreichbar beim Start, Zustimmung „automatisch“: keine Meldung, `lastCheck` bleibt, der nächste Start versucht es wieder (Test in Task 4).
2. Nur ein Script-Editor hat ungespeicherte Puffer, der Store ist sauber: Die Warnung vor dem Verlust erscheint trotzdem, und `update_install` bekommt `discardUnsaved: true` (Test in Task 4).
3. `localStorage` gesperrt oder kaputt: kein Absturz, Vorgaben gelten, die Frage nach der Zustimmung kommt höchstens einmal je Start (Tests in Tasks 3 und 4).
4. Ein unvollständiger Release (macOS-`.sig` fehlt, Fassung passt nicht zum Tag, Signatur kaputt): `latest.json` entsteht nicht, der Job scheitert vor dem Hochladen (Tests in Tasks 5 und 6).
5. Zweimal „Install…“ oder eine Prüfung aus dem Menü während einer laufenden: genau eine Installation, genau eine Prüfung (Tests in Tasks 2 und 4).
