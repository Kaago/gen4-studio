# Phase 4.2 „Build-Graph“ Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Der Build läuft nur noch die Schritte, deren Eingaben sich geändert haben. ARM9 und Overlays kommen aus einem BLZ-Cache, rotom und chatot haben `stat`-Tore, geänderte Member werden in das vorhandene NARC eingesetzt, die ROM entsteht weiter voll mit ds-rom. Das Ergebnis ist byte-gleich zum vollen Build und zur Basis-ROM. „Hier spielen“ braucht nach einer Karten-, Text- oder Scriptänderung warm ≤ 0,5 s, ohne Änderung ≤ 0,2 s. Technik › Prüfen und Bauen zeigt eine Zeile je Schritt.

**Architecture:** `crate::build` bleibt die Fassade (`build`, `prepare_for_build`, `build_prepared`, `pack_dir`, `extract_rom`; Signaturen unverändert). Darunter liegen neue Untermodule in `crates/g4-kernel/src/build/` (Rust-2018-Layout neben `build.rs`, kein Umzug der Datei): `salt` (Werkzeug-Salz aus `Cargo.lock`), `blz` (BLZ-Cache über die öffentliche ds-rom-API), `fingerprint` (`stat` zuerst, xxh3 bei Abweichung, racy-Regel), `state` (`.g4/build/state.json`), `step` (`Step`-Vertrag und Runner) und `steps` (rotom, chatot, Packen mit Einsetzen, Beobachten, ROM). Die Reihenfolge ist fest, Abhängigkeiten laufen über die Dateien: Ein Schritt schreibt nur bei geänderten Bytes (`write_if_changed`), also sieht der nächste Schritt nur echte Änderungen (early cutoff). Die Laderegel der Texte (`text_winner`, nach Zeit) weicht `text::TextSync` (nach Fingerabdrücken, gespeichert in derselben `state.json`).

**Tech Stack:** Rust (g4-kernel, ds-rom `8a9c151`, xxhash-rust xxh3, serde_json), Tauri-Befehle mit MCP-Zugriff, React 19 mit vitest, `scripts/gate.sh`.

**Spec:** [entscheidungen.md](../../research/2026-10-27-phase-4/entscheidungen.md): Abschnitte „Phasenschnitt und Reihenfolge“, „Build-Graph (Gutachten B, 4.2)“, die Zeile „`.g4/`“ unter „Git“, „Nebenaufgaben 4.0 und das Projektformat“, „Nicht in Phase 4“. Dazu [gutachten-b-build-graph.md](../../research/2026-10-27-phase-4/gutachten-b-build-graph.md) §1 bis §2 (Prototyp `gutachten-b-messung/src/main.rs`, Funktion `inc`) und [ROADMAP.md](../../ROADMAP.md) „Phase 4“, Eintrag 4.2 mit Gate.

| Eingaben `chatot` | `expanded/textArchives/` und `unpacked/textArchives/`. Läuft nur für Archive mit `TextSide::JsonNewer` oder `Unknown` (dann zuerst `member_is_current`), statt alle JSON zu dekodieren | B §2.2, die Dekodier-Prüfung entfällt bei vorhandenem Zustand |

Ein neuer Ausgabepfad oder eine gelöschte ROM ist eine „fehlende Ausgabe“, dann läuft der Schritt | Ohne Änderung gilt die ROM als aktuell (B §2.6, ≈ 0,06 s) |
| Fingerabdruck | `Fp { size, mtime_ns, ctime_ns, ino, xxh3: Option<u64> }`. Unix liest `ctime` und `ino` über `MetadataExt`, Windows setzt beide auf 0. Gleich heißt: alle `stat`-Felder gleich und kein racy-Fall. Weicht nur die Größe ab, ist die Datei geändert. Bei sonst abweichendem `stat` wird gehasht: Mit gleichem Hash wird nur der `stat` erneuert, sonst ist die Datei geändert, und ohne aufgezeichneten Hash gilt sie als geändert | `ctime` deckt die simulierte DSPRE-Änderung ab (Bytes an Ort und Stelle, gleiche Größe, mtime zurückgesetzt), die nur mit mtime unsichtbar bliebe |
| racy-Regel | Jeder Schritt-Eintrag speichert `scanned_at_ns`. Liegt die aufgezeichnete mtime nicht mindestens 2 s vor `scanned_at_ns`, gilt der Eintrag als racy: Er wird schon beim Aufzeichnen mit xxh3 gespeichert und beim Vergleich über den Inhalt geprüft, auch wenn der `stat` gleich ist | B §2.2, Regel von Git; deckt FAT/exFAT mit 2 s ab |
| Werkzeug-Salz | `crates/g4-kernel/build.rs` liest `../../Cargo.lock` zeilenweise (keine neue Build-Abhängigkeit) und gibt `G4_LOCK_DS_ROM`, `G4_LOCK_ROTOM`, `G4_LOCK_CHATOT`, `G4_LOCK_UXIE` als `"<name> <version> <source>"` aus, sonst `"unknown"`, dazu `rerun-if-changed=../../Cargo.lock`. Salz je Schritt: `step_salt(tool, rev)` = Lock-Zeile + `#<rev>`; die Revisionen sind Konstanten in `steps.rs` (`ROTOM_REV`, `CHATOT_REV`, `PACK_REV` (NARC-Writer), `ROM_REV`), alle 1 | B §2.2; ein Kernel-Update ohne Werkzeugwechsel kostet keinen vollen Build |
| `build.cache-stale` | kein Eintrag im Katalog. Der Runner setzt `StepReport.reason = Some("build.cache-stale")` bei einem Salzwechsel, andere Gründe sind `"no-state"` (auch nach „ohne Cache“), `"output-changed"`, `"removed"` | „intern, ohne Anzeige“; das Gate liest den Grund aus `--timings` |
| Speicher | `.g4/build/state.json`: `{ "version": 1, "steps": { id: { "salt", "scanned_at_ns", "inputs": { relpfad: Fp }, "outputs": { relpfad: Fp }, "ms" } }, "texts": { "0012": { "json": Fp \| null, "member": Fp \| null } }, "rom": { "path", "fp" } }`, ein Fp als Array `[size, mtime_ns, ctime_ns, ino, "xxh3hex" \| null]`. Fehlt die Datei, ist sie kaputt oder hat sie eine andere `version`, gilt ein leerer Zustand (voller Build, kein Fehler). Geschrieben wird über `BuildState::update(root, f)` (laden, ändern, atomar schreiben unter einem prozessweiten `Mutex`), damit ein Speichern im Store und ein Build ohne Lock sich nicht überschreiben. BLZ unter `.g4/build/blz/arm9-<xxh3>.blz` und `ov<NNN>-<xxh3>.blz` | B §2.3; dieselbe Datei trägt den DSPRE-Abgleich von 4.3b |
| Eintrag nach Fehler | Ein Schritt bekommt seinen Eintrag erst nach Erfolg. Scheitert er, wird sein alter Eintrag gelöscht, damit der nächste Build ihn voll laufen lässt. `prepare_for_build` schreibt die Einträge von `rotom` und `chatot`, `build_prepared` die übrigen und `rom` | Ein abgebrochener Build darf nichts als aktuell markieren |
| BLZ-Cache | `Rom::load` mit `RomLoadOptions { compress: false, .. }`. Für jedes Overlay mit `originally_compressed()` ist der Schlüssel xxh3 von `full_data()`. Ein Treffer setzt `Overlay::new(bytes, OverlayOptions { originally_compressed: true, info })` mit `info.compressed = true` ein, ein Fehlschlag ruft `compress()` und legt die Datei ab. ARM9 ebenso über `Arm9::new(bytes, *arm9.offsets())`. Ist in `arm9_overlays/overlays.yaml` ein Overlay `signed: true` (eigener serde-Typ, nur dieses Feld), lädt der Build wie heute mit `compress: true` (`BlzReport.fallback = true`) | B §2.4, Prototyp `inc`; signierte Overlays gibt es in den drei Spielen nicht |
| Einsetzen ins NARC | `pack:<art>` inkrementell: `Narc::read(gepackt)`, geänderte Member ersetzen, neue nur anhängen, wenn sie lückenlos ab `len` folgen, dann `write_if_changed`. Voll packt es (`pack_dir`) bei gelöschtem Member, bei fehlendem gepacktem NARC, bei einem NARC, das sich gegen den Eintrag geändert hat, oder ohne Eintrag | B §2.5 Variante B |
| Elternordner | `write_if_changed` legt den Elternordner des Ziels an (`create_dir_all`) | C §2.2: ein Klon ohne die ignorierten NARCs |
| Laderegel der Texte | `text::TextSync::side(n)` liefert eines von `Neither`, `OnlyJson`, `OnlyMember`, `InSync` (keine Seite geändert), `JsonNewer`, `MemberNewer`, `Conflict` und `Unknown` (kein Eintrag). Sind beide Seiten geändert und hält der Member schon die Texte der JSON (`member_is_current`), gilt `InSync`: ein Git-Wechsel, der beide Seiten passend tauscht, ist kein Konflikt. JSON gelesen wird bei `OnlyJson`, `InSync`, `JsonNewer`, `Unknown` und `Conflict`, der Member bei `OnlyMember` und `MemberNewer`. | Konflikt beim Bauen | `chatot` gibt bei mindestens einem `Conflict` `Err(KernelError::TextConflict(Vec<u16>))` zurück, bevor etwas geschrieben ist. Der Befehl heißt `resolve_text_conflicts`. Über MCP ist er unumkehrbar mit dem Grund „Eine Fassung eines Textarchivs überschreiben“ | „beide neu → Konflikt mit Rückfrage“, nie still überschreiben |

- Ein kopiertes oder geklontes Projekt mit kopiertem `.g4/build/` (alle Inode und ctime anders): Der erste Build hasht, fragt nie nach einem Text-Konflikt und ist byte-gleich (Task 3, `a_copied_project_with_its_state_asks_nothing`).
